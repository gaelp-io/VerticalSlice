## Milestone 1 Devlog
1. One visual scripting graph in my game is the player's script machine which handles the smooth movement. I used the On Input System Event Vector 2 in order to make my movement alongside the inputs of a keyboard (WASD). Orginally I used transform translate however this led to jittery/vibrating collisions with the invisible borders in my game. In order to prevent this I went with rigidbody 2D nodes instead of transform translates. At first I wasn't having trouble and actually got smoother movement without any collision issues. However, I had realized that the player wouldn't stop when the keys were released because the logic in the rigidbody 2D node was to set it's velocity. So even though the On Input System Vector 2 node was set to On Hold, the player would keep moving in whichever direction (or key) they last pressed. After some trial and error I tried a solution where I would have two On Input System Event Vector 2 nodes where one handled the movement I had alreayd and the second would solely be connected to a single node that would set the Rigidbody 2D velocity back to 0,0 which effectively would stop movement. I realized this as a solution because the On Released chocie for the On Input System Event Vector 2 would stop movement whenever a key was released which is exactly what I was looking for. Then, the actual movement nodes started at the On Hold, On Input System Event Vector 2 node where I would set the vector 2 value into a get x and get y node, then multiple those two nodes with their own get variable (for speed) and then input those outcomes into a create vector 2 node in order to be able to input that new value into the set rigidbody 2D velocity which would create the smooth movement for the player.

&nbsp;&nbsp;&nbsp;&nbsp;What I updated in my break-down was simply adding another bubble that contains the basic information of the state machine and connecting it to the other appropriate bubbles. First, I described the state machine as having two states: normal state and speedboost state. The player starts off in the normal state with an average speed, then if the player picks up a power-up they transition to the speedboost state which gives them a faster speed than normal, however this state only lasts for 10 seconds. In my break-down I also described how when the speedboost is obtained, there is a visual timer that informs the player how long they have left with their speed boost. The state machine bubble in my break-down connects to the player and the UI. The bubble connects to the player because it is the player gameobject that has the statemachine and detects whenever it enters the collider of the speedboost gameobject and starts the transition from normal state to speedboost state. I also connected the statemachine to the UI because once the player switches into the speedboost state a visual timer appears to let them know how much time they have remaining with the speedboost.

&nbsp;&nbsp;&nbsp;&nbsp;The way my state machine works is that the starting state is the "normal state" where the player begins the game with their speed variable set to 3 for an average speed. Then, whenever the speedboost prefab spawns, the statemachine transition stage checks for an on trigger 2D event to see if the player hits a gameobject with the tag "speedboost". If the player does, then the state machine triggers the transition into the "speedboost state" where the player has their speed variable set to 10 in order to give the player the feeling of obtaining a speedboost. Then, once the speedboost state is entered, the transition from speedboost to normal occurs after 10 seconds via a timer node that triggers the transition. Ultimately, I kept the state machine logic pretty simple after having difficulty getting it to work with more complicated nodes and logic. The other systems this state machine works alongside are the visual timer that pops up once the speedboost power up is obtained and the destruction of the scene prefab of the power up. For the desctrution of the scene prefab of the power up, I simply added a script that would detect the "player" tag which would then call the destroy method. This way, once the prefab collides with the player it destroys itself, I opted to go with this method because I wasn't able to properly add the destruction of the scene prefab because it would only lead to the error of destroying the prefab from the entire project itself which is not what I wanted. Then, for the timer I also created a script similar to the other timer in my game except I did a bit of research in order to get this cool effect of a circle slowing disppearing like a pie to show the player their time left with the power up visually instead of having them read more text. This timer also starts once the player hits a gameobject with the tag "speedboost" so that it is lined up with the transition of the player's state going from "normal" to "speedboost".

### Devlog Question 3
How I bridged visual scripting and code in my project was by having my visual scripting graph call a method from my player's script that would activate the BoostTimerUI everytime the player would trigger a collider of a gameobject labeled boost. It uses OnTriggerEnter2D, just like my state machines uses to check if a player picked up a boost, and if it detects that the player has touched the boost clone, then it gets a component which is my player's script (player boost trigger) from "This" gameobject which is the player gameobject, and then it invokes the method "ActivateBoostUI" from the player's script which activates the BoostTimerUI. This allows the BoostTimerUI to be activated whenever the player's collider comes in contact with the speed boost's collider, no matter how many times that may happen.

## Final Devlog
1. The core gameplay loop consists of surviving for as long as possible while driving through three lanes and avoiding incoming obstacles. The player can collect speed boosts to temporarily increase movement speed and life pickups to restore lost lives. As time progresses, a hostile enemy vehicle periodically appears and chases the player. If the enemy catches the player, a Quick Time Event (QTE) begins where the player must rapidly press the spacebar to escape. Successfully completing the QTE damages the enemy, while failing causes the player to lose a life. The game ends when the player runs out of lives, and the player's survival time is recorded. The content included in this Vertical Slice demonstrates the major systems and player experiences that are planned for the full game. Players can experience obstacle avoidance, power-up collection, enemy encounters, risk-versus-reward decision making, and progression through their increasing survival time. These mechanics showcase the intended balance between routine driving gameplay and high-intensity enemy encounters. While the full game will include additional enemy types, power-ups, environments, and more varied challenges in order to increase uniqueness for every playthrough, this Vertical Slice demonstrates the core gameplay loop and provides a sample of what the complete game experience would be like.
2. My rendering effect is activated through gameplay logic in the QTEManager.cs script. When the player collides with the enemy and a Quick Time Event (QTE) begins, the script changes the player's SpriteRenderer material from a normal material to a special QTE material using playerRenderer.material = qteMaterial;. This causes the player to immediately display a different visual effect during the QTE. When the QTE ends, either through success or failure, the script restores the original material using playerRenderer.material = normalMaterial;. The effect is triggered entirely through C# gameplay logic and technically, the system works by accessing the player's SpriteRenderer component and swapping the material assigned to it at runtime, allowing a custom Shader Graph effect to be enabled and disabled in response to gameplay events. The implementation can be found in QTEManager.cs, specifically in the StartQTE(), Success(), and Failure() methods where the material changes occur. In order to see this occur within the game, the playtester will have to last a minute in order to encounter the enemy, where they will then collide with the player and change the player's material from normal to a redder material/color.
3. For future projects, I will definitely be utilizing bubble diagrams and task step break-downs in my planning process. Bubble diagrams will be extremely useful for planning the major parts of a vertical slice and overlooking the major systems within the game and how they interact with one another. Task step break-downs are also extremely useful as they would allow me to see exactly how I plan to implement a certain feature or mechanic in my game without having many bugs or issues along the way or after the implementation of said feature/mechanic. The task step break-downs are also useful for visualizing the scope of my project along side the bubble diagram. While the bubble diagram shows me the grand scheme of things, the task step break-downs allow me to actually calculate the scope of the project by seeing how long each feature and mechanic may take to implement. This allows me to be able to either cut ideas if I don't believe I will have enough time, or even add new ideas or features if I see that I have extra time to spare. I believe it is also important to constantyl update your bubble diagram in order to see how your new systems fit into your game and how they connect with the other systems that you have already established previously. The plan I've described is actually pretty similar to my process creating this vertical slice. The only difference I'd say is that I didn't utilize the task step break-down as much as I could've. My bubble diagram went through various changes throughout my project, and things didn't go according to plan but I wouldn't say that is a negative thing. Instead I was able to make my vertical slice evolve into a game that I enjoyed making which definitely helped throughout the entire process. By letting my game change and evolve into what it is now, I was able to both visualize my brand new ideas while also enjoying the entire process along the way!
